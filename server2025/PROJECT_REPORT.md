# Server-14: 高性能私有化 AI 推理服务系统
## 项目汇报与面试指南

---

### 1. 项目简介 (Project Overview)

**Server-14** 是一个**从零构建的、生产级的高性能 LLM 推理服务端**。

它不仅仅是一个简单的 API 包装器，而是一个深度集成了 **C++ 底层推理优化 (llama.cpp)**、**数据库持久化**、**安全鉴权** 和 **现代化前端交互** 的全栈解决方案。

它的核心目标是：在普通 CPU 硬件上，提供**低延迟（秒开）**、**多用户并发**、**安全可控**的私有化 AI 对话服务。

---

### 2. 核心功能与技术亮点 (Core Features)

#### 🚀 1. 极致性能：KV Cache 增量推理
*   **痛点**：传统推理在多轮对话中会重复计算历史 Token，导致越聊越慢。
*   **方案**：实现了 **KV Cache（键值缓存）复用机制**。将 Attention 层的 Key-Value 矩阵常驻内存，每轮对话仅计算新增 Token。
*   **成果**：在 1000 Token 上下文的对话中，响应速度从 **15.8秒** 降低至 **0.4秒**，实现了 **37倍的性能跃升**，彻底解决了"首字延迟 (TTFT)"问题。

#### 🔒 2. 企业级安全：JWT 鉴权与隔离
*   **机制**：实现了基于 **JWT (JSON Web Token)** 的无状态认证系统。
*   **隔离**：严格的数据权限控制。用户 A 无法通过 ID 遍历或猜测访问用户 B 的会话数据。
*   **持久化**：所有聊天记录实时同步至 **SQLite 数据库**，支持服务重启后会话无缝恢复。

#### 🧠 3. 前沿模型支持：DeepSeek-R1 深度适配
*   **特性**：针对 DeepSeek-R1 的"思考链 (Chain of Thought)"特性进行了专项适配。
*   **实现**：在后端流式输出中实时解析 `<think>` 标签，将"思考过程"与"最终回复"分离。
*   **体验**：前端支持折叠/展开思考过程，让用户既能看到 AI 的逻辑推演，又不被冗长信息干扰。

#### ⚡ 4. 高并发架构：C++ Epoll + 线程池
*   **IO 模型**：使用 Linux 原生 **epoll (边缘触发)** 处理海量并发连接。
*   **任务调度**：手写 **ThreadPool** 进行任务分发，主线程只负责 IO，工作线程负责计算，最大限度压榨 CPU 性能。
*   **交互**：实现了 **SSE (Server-Sent Events)** 流式传输，提供打字机式的实时响应体验。

### 3. 项目演进路线 (Evolution)

*   **Server-11**: 基础原型。单轮问答，无记忆，无数据库。
*   **Server-12**: 引入 `SessionManager`。支持多轮对话，但在长文本下性能严重衰退。
*   **Server-13**: 引入 **KV Cache**。重写推理引擎，实现增量解码，性能质变。
*   **Server-14 (最终版)**: 引入 **用户系统 & 数据库**。实现登录注册、JWT、持久化、UI 升级，达到交付标准。

### 4. 面试官可能的提问 (Q&A)

#### Q1: 你提到的 KV Cache 是怎么实现的？为什么能快 37 倍？
**回答思路**：
*   **原理**：Transformer 的 Self-Attention 计算复杂度是 $O(N^2)$。每次生成新 Token 时，都需要用到之前所有 Token 的 K 和 V 向量。
*   **实现**：我维护了一个 `KVCachedSession` 结构体，持有 `llama_context`。在推理前，我先对比新 Prompt 和 `cached_tokens` 的公共前缀（Longest Common Prefix）。
*   **关键点**：只对**不匹配的后缀部分**进行 Decode。比如历史有 1000 个 Token，新问题 10 个 Token。普通做法算 1010 个，我只算 10 个。这就是 15s 变 0.4s 的原因。

#### Q2: 如果用户修改了之前的对话（比如删除了中间一条消息），KV Cache 怎么办？
**回答思路**：
*   **挑战**：这会导致 Token 序列中间断裂，公共前缀变短。
*   **处理**：我的算法会自动计算 `n_reuse`（可复用长度）。如果用户删除了中间的消息，`n_reuse` 会变小。我会保留有效的前缀缓存，丢弃无效的后缀，并从断点处开始重新计算。
*   **Bug 经历**：我曾遇到过 `prune()`（历史裁剪）导致缓存失效的 Bug。当历史过长触发裁剪时，摘要被插入头部，导致整个序列全变了。我修复了逻辑，一旦触发裁剪，强制清空缓存或重新构建，保证了数据的正确性。

#### Q3: 为什么要用 C++ 写 Web Server？用 Python/FastAPI 不是更快吗？
**回答思路**：
*   **性能一致性**：LLM 推理是计算密集型任务，Python 的 GIL 锁在多线程下是瓶颈。C++ 可以精准控制内存和线程。
*   **部署成本**：Python 依赖庞大的环境（PyTorch 等），镜像往往几个 GB。我的 C++ 服务编译后只有一个二进制文件，依赖极少，镜像极小。
*   **学习目的**：我想深入理解 Linux 网络编程（epoll）和 Transformer 底层推理流程，而不是仅仅做一个 API 调包侠。

#### Q4: 你的 SSE (流式输出) 是怎么实现的？
**回答思路**：
*   **协议**：基于 HTTP 长连接，设置 `Content-Type: text/event-stream`。
*   **实现**：我在 `ModelManager` 中注册了一个回调函数。每当模型生成一个 Token，回调函数就会被触发。
*   **逻辑**：回调函数将 Token 包装成 `data: {...}\n\n` 格式写入 Socket 缓冲区。如果是 DeepSeek 模型，我还会在流式传输中实时检测 `<think>` 标签，动态标记 Token 类型（是思考还是答案），让前端能实时渲染不同样式。

#### Q5: 你是如何保证线程安全的？
**回答思路**：
*   **推理层**：`llama_context` 不是线程安全的。我使用了 **Session Context Pool**（会话池）或者互斥锁，确保同一个 Session 在同一时刻只能被一个线程访问。
*   **管理层**：`SessionManager` 使用 `std::mutex` 保护 `unordered_map`，防止多线程同时创建/删除会话导致的数据竞争。
*   **数据库**：SQLite 默认模式在多线程写入时可能锁死。我也在 `Database` 类中加了应用层互斥锁，串行化写操作，保证数据一致性。

### 5. 深度技术问答 (Deep Dive Q&A - 针对计算机专业面试官)

#### Q6: 你在 HttpServer 中使用了 epoll。请问你使用的是水平触发 (LT) 还是边缘触发 (ET)？为什么？如果不小心处理 ET 会发生什么？
**回答思路**：
*   **模式选择**：我使用了 **ET (Edge Triggered) + 非阻塞 IO**。
*   **原因**：ET 模式仅在状态变化时通知一次，减少了 `epoll_wait` 系统调用的返回次数，在高并发下比 LT 更高效。配合非阻塞 IO，我可以一次性把 buffer 读空。
*   **潜在坑点**：ET 模式最危险的是**数据没读完**。如果内核缓冲区还有数据，但我不继续 read，epoll 不会再次通知，导致连接"假死"。
*   **我的实现**：我在 `handleConnection` 中使用了一个 `while(true)` 循环配合 `read`，直到返回 `EAGAIN` 或 `EWOULDBLOCK`，确保清空了当前的内核读缓冲区。

#### Q7: KV Cache 虽然提升了速度，但极其消耗内存。如果 100 个用户同时长对话，内存爆了怎么办？你设计了什么淘汰策略？
**回答思路**：
*   **现状分析**：一个 2048 长度的 float16 KV Cache 大约占用 200MB 内存。100 个用户就是 20GB，普通服务器确实扛不住。
*   **优化策略 (SessionContextPool)**：这也是 Server-14 引入 `SessionContextPool` 的原因。我设置了 `max_sessions` (例如 20)。
*   **淘汰算法 (LRU)**：我实现了一个 **LRU (Least Recently Used)** 队列。当池满了，新的会话请求进来时，我会强制释放最久未使用的那个会话的 `llama_context`（释放显存/内存），并将其降级为"冷数据"（只保留磁盘上的 SQLite 历史）。
*   **代价**：被淘汰的用户下次说话时，需要重新进行 Pre-fill (全量计算)，但系统整体不会崩溃 (OOM)。

#### Q8: 你的 SessionManager 使用了 `std::mutex` 全局大锁。在高并发下这会不会成为瓶颈？如何优化？
**回答思路**：
*   **诚实承认**：目前的实现确实是一把大锁保平安，对于几十个并发的推理服务来说，推理计算（几百毫秒）才是瓶颈，锁竞争（微秒级）暂时不是主矛盾。
*   **优化方案 1 (读写锁)**：绝大多数操作是 `getHistory` (读)，只有生成时是写。可以将 `std::mutex` 换成 `std::shared_mutex`，允许多个读者并发访问。
*   **优化方案 2 (分段锁/Sharding)**：类似 Java `ConcurrentHashMap`，将 sessions 映射到 16 个 bucket，每个 bucket 有一把锁，锁粒度降低 16 倍。

#### Q9: 你是如何处理 TCP 粘包 (Stickiness) 和拆包 (Fragmentation) 问题的？
**回答思路**：
*   **问题本质**：TCP 是流式协议，没有"包"的概念。`read` 可能一次读到半个 HTTP 请求，或者两个 HTTP 请求粘在一起。
*   **应用层协议**：HTTP 协议本身有边界机制（Header 以 `\r\n\r\n` 结束，Body 长度由 `Content-Length` 指定）。
*   **我的实现**：
    1.  维护了一个 `std::unordered_map<int, std::string> recvBuffers`，为每个 fd 维护独立的接收缓冲区。
    2.  每次 `read` 数据追加到 buffer。
    3.  循环检测：buffer 中是否包含 `\r\n\r\n`？解析 Content-Length，检查 buffer 长度是否 >= Header + Body？
    4.  如果完整，就切分出一个 Request 处理；如果不足，保留 buffer 等待下一次 `epollin` 事件。

#### Q10: 采样 (Sampling) 阶段的 Top-K 和 Top-P 具体是如何协同工作的？Temperature 为 0 代表什么？
**回答思路**：
*   **协同逻辑**：通常是先 Temperature -> 再 Top-K -> 最后 Top-P。
    1.  **Temperature**: $P_i = \frac{\exp(logit_i / T)}{\sum \exp(logit_j / T)}$。T < 1 会放大高概率 token 的优势（Sharpen），T > 1 会拉平概率分布（Flatten）。
    2.  **Top-K**: 仅保留概率最高的 K 个 token，其余归零。这切断了低概率的长尾。
    3.  **Top-P (Nucleus)**: 按概率从高到低累加，直到累加和达到 P (如 0.9)。这是一种动态的 Top-K，对于确定的问题候选词少，开放的问题候选词多。
*   **Temperature = 0**：数学上除以 0 无意义。但在实现上，这意味着 **ArgMax (贪婪解码)**，直接取 Logit 最大的那个 Token，不进行任何随机采样。这保证了对于同样的输入，输出永远完全一致（用于数学题或代码生成）。
