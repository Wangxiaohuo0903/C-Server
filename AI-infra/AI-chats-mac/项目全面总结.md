## 1. 项目概览

### 1.1 研究背景

**核心问题**: 大语言模型推理需要强大算力，传统方案依赖云端GPU，存在以下问题：
- 隐私泄露风险（数据需上传云端）
- 网络延迟高（100-500ms往返）
- 云端成本昂贵（GPU租用费用高）
- 离线场景无法使用

**解决方案**: 在边缘设备（消费级硬件）上部署LLM推理服务
- 数据本地处理，保护隐私
- 零网络延迟
- 一次部署，长期免费使用
- 支持离线工作

### 1.2 项目目标

**主目标**: 在消费级硬件上实现< 1秒的LLM推理延迟

  ```

    1. 遍历Trie树: H → e → l → l → o → ...
    2. 找到最长匹配前缀: "Hello world, my"
    3. 返回对应的KV-Cache指针

  ```

#### D. SpeculativeDecoder (`src/inference/SpeculativeDecoder.h/cpp`)
- **原理**: 小模型起草（Draft），大模型校验（Verify）
- **工作流程**:
  ```
  传统贪婪解码:
  Step 1: 生成token A  (175ms)
  Step 2: 生成token B  (175ms)
  Step 3: 生成token C  (175ms)
  总耗时: 525ms

  推测式解码:
  Step 1:
    - Drafter起草5个tokens: [A, B, C, D, E]  (175ms)
    - Verifier批量校验: 接受前3个 [A✓, B✓, C✓, D✗, E✗]  (109ms)
    - 总耗时: 284ms，一次生成3个token
  理论加速: 525ms / 284ms = 1.85x
  ```
- **关键参数**:
  - `K`: 每次起草的token数量（动态调整2-8）
  - `acceptance_rate`: 接受率（目标60-70%）
  - `temperature`: 采样温度（影响接受率）

## 3. 核心理论知识

### 3.1 大语言模型推理基础

#### A. Transformer架构
```
Input tokens → Embedding → [Transformer Blocks x 32] → Output logits
                              ↓
                    ┌─────────────────┐
                    │ Transformer块    │
                    │ ├─ Self-Attention│  ← 计算注意力（最耗时）
                    │ ├─ Feed-Forward  │  ← 全连接层
                    │ └─ Layer Norm    │  ← 归一化
                    └─────────────────┘
```

**计算瓶颈**:
- Self-Attention: O(n²d)，n为序列长度，d为隐藏维度
- 7B模型：32层 × 4096维度 = 巨大计算量

#### B. 自回归生成
```python
# 伪代码
def generate_token(prompt):
    context = tokenize(prompt)
    for i in range(max_tokens):
        # 每次生成1个token，需要完整前向传播
        logits = model.forward(context)  # ← 耗时！
        next_token = sample(logits)
        context.append(next_token)
        yield next_token
```

**问题**: 每生成1个token，都需要重新计算所有历史token的注意力

#### C. KV-Cache优化原理

**Self-Attention公式**:
```
Attention(Q, K, V) = softmax(Q·K^T / √d) · V
```

**关键发现**: 已生成token的K和V不会改变！

**优化策略**:
```python
# 无KV-Cache（慢）
def generate_without_cache(context):
    for pos in range(len(context)):
        K[pos] = linear_k(hidden[pos])  # 重复计算！
        V[pos] = linear_v(hidden[pos])  # 重复计算！
    attention = Q @ K.T @ V

# 有KV-Cache（快）
def generate_with_cache(context, kv_cache):
    # 只计算新token的K和V
    new_K = linear_k(hidden[-1])  # 只算1个
    new_V = linear_v(hidden[-1])
    kv_cache.append(new_K, new_V)  # 缓存复用
    attention = Q @ kv_cache.K.T @ kv_cache.V
```

**加速效果**:
- 单token生成: 从O(n²) → O(n)
- 实测: 首token ~200ms，后续token ~30ms

### 3.2 前缀缓存（本项目核心创新）

#### A. 问题场景
```
用户A: "写一个Python函数计算斐波那契数列"
用户B: "写一个Python函数计算质数"
用户C: "写一个Python函数排序数组"
```

**观察**: 所有请求都有相同前缀 "写一个Python函数"

#### B. 传统方案的浪费
```
请求1: [写, 一, 个, Python, 函, 数, 计, 算, ...]
       ↓ 计算KV-Cache

请求2: [写, 一, 个, Python, 函, 数, 排, 序, ...]
       ↓ 重新计算相同前缀的KV-Cache（浪费！）
```

#### C. 前缀缓存方案
```
第一次请求:
  输入: "写一个Python函数计算斐波那契数列"
  1. 计算完整KV-Cache
  2. 存储前缀 "写一个Python函数" 的KV-Cache

第二次请求:
  输入: "写一个Python函数排序数组"
  1. 匹配到前缀 "写一个Python函数" (7个token)
  2. 直接加载缓存的KV-Cache
  3. 只需计算 "排序数组" (4个token)
  节省时间: 7/11 = 64%
```

#### D. 实现细节：Prefix Tree (Trie)

**数据结构**:
```cpp
struct TrieNode {
    int token;                           // 当前token ID
    std::unordered_map<int, TrieNode*> children;  // 子节点
    KVCacheData* cache_data;             // 缓存数据
    int depth;                           // 深度（用于匹配长度）
};

class PrefixTree {
    TrieNode* root;

    // 插入token序列
    void insert(vector<int> tokens, KVCacheData* cache);

    // 查找最长前缀匹配
    PrefixMatch findLongestPrefix(vector<int> tokens);
};
```

**匹配算法**:
```
输入: [1, 2, 3, 4, 5]
Trie树:
      root
      ├─ 1 (缓存: seq1)
      │  ├─ 2 (缓存: seq12)
      │  │  └─ 3 (缓存: seq123)
      │  │     └─ 4 (缓存: seq1234)  ← 最长匹配
      │  └─ 7 (缓存: seq17)
      └─ 6 (缓存: seq6)

匹配过程:
  1. 从root开始，查找token 1 → 找到
  2. 从节点1，查找token 2 → 找到
  3. 从节点2，查找token 3 → 找到
  4. 从节点3，查找token 4 → 找到
  5. 从节点4，查找token 5 → 未找到
  6. 返回匹配: [1,2,3,4]，深度4
```

**时间复杂度**:
- 插入: O(n)
- 查找: O(m)，m为输入长度
- 空间: O(总token数)

### 3.3 推测式解码（Speculative Decoding）

#### A. 核心思想

**动机**: 小模型快但不准确，大模型慢但准确
**策略**: 让小模型先"猜"几个token，大模型一次性验证

#### B. 算法流程

```python
def speculative_decode(prompt, K=5):
    context = prompt
    generated = []

    while len(generated) < max_tokens:
        # 第1步: Drafter起草K个tokens
        draft_tokens = []
        for i in range(K):
            token = drafter_model.generate(context)  # 小模型，快
            draft_tokens.append(token)
            context.append(token)

        # 第2步: Verifier批量校验
        # 关键：使用batch inference，一次前向传播验证K个token
        accepted = []
        for i, token in enumerate(draft_tokens):
            verifier_prob = verifier_model.get_prob(context[:len(prompt)+len(accepted)+1])
            drafter_prob = drafter_model.get_prob(context[:len(prompt)+len(accepted)])

            # 概率匹配校验
            if verifier_prob[token] / drafter_prob[token] > random():
                accepted.append(token)  # 接受
            else:
                break  # 拒绝，停止后续验证

        # 第3步: 处理结果
        if len(accepted) == 0:
            # 全部拒绝，verifier自己生成1个
            token = verifier_model.generate(context[:len(prompt)+len(generated)])
            accepted = [token]

        generated.extend(accepted)
        context = prompt + generated

    return generated
```

#### C. 理论分析

**加速比公式**:
```
加速比 = (接受的token数) / (推理步数)

理想情况（接受率100%）:
  每步接受K个token → 加速K倍

实际情况（接受率60%）:
  每步平均接受 0.6K 个token
  额外bonus: verifier拒绝时会生成1个新token
  实际加速比 ≈ (0.6K + 1) / 1 = 0.6K + 1

  K=5时: 加速 0.6×5 + 1 = 4倍
```

**成本分析**:
```
贪婪解码成本:
  生成100个token = 100步 × T_verify

推测式解码成本:
  假设接受率60%, K=5
  步数 = 100 / (0.6×5 + 1) ≈ 25步
  每步成本 = T_draft + T_verify
  总成本 = 25 × (T_draft + T_verify)

加速条件:
  25 × (T_draft + T_verify) < 100 × T_verify
  T_draft < 3 × T_verify

结论: Drafter必须比Verifier快3倍以上才有效
```

#### D. 关键挑战

**挑战1: Drafter与Verifier的匹配**
- 问题: TinyLlama (1.1B) vs Llama-2 (6.7B)，能力差距6倍
- 结果: 接受率仅20%，远低于目标60%
- 解决: 需要更强的drafter（如Llama-2 3B）

**挑战2: 温度对接受率的影响**
```
低温度 (T=0.1):
  - 输出确定性高
  - Drafter和Verifier更容易对齐
  - 接受率: 40-50%

高温度 (T=0.9):
  - 输出随机性大
  - Drafter和Verifier分布divergence大
  - 接受率: 10-20%
```

**挑战3: 硬件异构调度**
- Drafter在CPU: 702ms/step（慢！）
- Verifier在GPU: 109ms/step
- 解决: 将Drafter也offload到GPU: 175ms/step

### 3.4 本项目的算法创新

#### A. 滑动窗口接受率追踪
```cpp
// 传统方法：只看全局接受率
float global_rate = total_accepted / total_drafted;  // 滞后

// 创新方法：滑动窗口（最近10步）
float recent_rate = sum(last_10_steps) / 10;  // 实时
```

**优势**: 快速响应任务特征变化，动态调整策略

#### B. 温度自适应K值调整

**算法**:
```cpp
float temp_factor = 1.0f;
if (temperature > 0.7f) {
    temp_factor = 0.7f;   // 高温度：减小K
} else if (temperature < 0.3f) {
    temp_factor = 1.3f;   // 低温度：增大K
}

float adjusted_target = base_acceptance_rate * temp_factor;
// 根据调整后的目标动态更新K值
```

**原理**: 高温度降低接受率，应减小K减少浪费

#### C. 基于加速比的闭环优化

**策略**:
```cpp
// 直接优化最终目标（加速比），而非中间指标（接受率）
float speedup = total_accepted / total_steps;

if (speedup < 1.2f) {
    // 效果不佳，减小K
    K = max(min_K, K - 1);
} else if (speedup > 2.0f && acceptance_rate > 0.6f) {
    // 效果优秀，尝试增大K
    K = min(max_K, K + 1);
}
```

#### D. Early Stopping机制

**条件**:
1. 接受率 < 15% → 推测式解码严重失效
2. 加速比 < 1.0x → 反而变慢
3. Draft/Verify时间比 > 5x → Drafter太慢

**作用**: 及时警告，避免负优化

#### Phase 2: 动态批处理 (Continuous Batching)

**目标**: 吞吐量提升2x，支持5-10并发用户

**核心技术**:
```python
# 传统静态批处理（不灵活）
def static_batch(requests):
    # 等待凑齐batch_size个请求才开始
    while len(pending) < batch_size:
        wait()
    batch_infer(pending)

# 动态批处理（Continuous Batching）
def continuous_batch():
    active_requests = []

    while True:
        # 新请求立即加入
        if has_new_request():
            active_requests.append(new_request)

        # 批量推理一步
        for req in active_requests:
            req.generate_one_token()

        # 完成的请求移除
        active_requests = [r for r in active_requests if not r.done()]
```

**优势**:
- 新请求无需等待
- 完成的请求立即释放资源
- GPU利用率更高

**挑战**:
- 不同请求的序列长度不同（需要padding）
- KV-Cache管理复杂
- 调度策略设计

**参考工作**: vLLM, FastGen, Orca

**动机**: 进一步降低内存占用和延迟

**技术**:
- INT8量化 → INT4量化
- 混合精度 (部分INT8, 部分FP16)
- 动态量化

**预期收益**: 内存-50%, 速度+20%

#### 方向2: 知识蒸馏

**动机**: 训练专用的Drafter模型

**方法**:
```
Teacher: Llama-2-7B
Student: TinyLlama-1.1B

训练目标:
  minimize KL_divergence(P_teacher || P_student)

数据集:
  - 代码生成任务 (10k样本)
  - 从Llama-2-7B采样生成
```

**预期**: 接受率 20% → 40%

**工作量**: 2-3周 + GPU训练时间

#### 方向3: 树形推测 (Tree-based Drafting)

**原理**: 不是顺序draft K个tokens，而是draft树状候选

**示例**:
```
Sequential Draft (K=5):
  draft: [A, B, C, D, E]
  verify: [A✓, B✓, C✗]
  → 接受2个

Tree-based Draft:
  draft:
      A
     /|\
    B C D
    |   |
    E   F
  verify: 找最长有效路径 A→B→E
  → 接受3个（更多！）
```

**预期**: 在相同计算量下，提升30-50%接受数量

**挑战**:
- 实现复杂度高
- 需要重构batch verification

**工作量**: 1-2个月
