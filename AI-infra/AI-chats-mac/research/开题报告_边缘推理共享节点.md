## 一、研究背景与问题动机

### 1.1 现有方案的局限性

当前大语言模型（LLM）部署主要有两种模式：

#### **模式1：云端API服务**（如ChatGPT、Claude）
- ❌ **成本高**：按token计费，重度使用成本高昂
- ❌ **隐私风险**：敏感数据需上传到云端
- ❌ **网络依赖**：弱网/离线场景无法使用
- ❌ **延迟不可控**：跨地域网络延迟影响体验

#### **模式2：本地单机部署**（如Ollama）
- ❌ **设备要求高**：每台设备都需安装LLM
- ❌ **资源重复占用**：家庭多台设备重复运行模型
- ❌ **移动设备限制**：手机/平板无法运行LLM
- ❌ **无法共享优化**：每台设备独立计算，缓存不互通

### 1.2 目标诉求与研究定位

**目标场景**：家庭/小团队（2-10人）共享使用LLM

**核心诉求**：
- ✅ **低成本**：一台设备服务多人，避免重复投入
- ✅ **隐私保护**：数据不出内网，本地计算
- ✅ **低延迟**：局域网访问，响应速度快
- ✅ **易部署**：树莓派/NUC等低成本设备可运行
- ✅ **跨设备访问**：手机/平板/电脑通过HTTP API使用

**研究定位**：填补Ollama（单机）与vLLM（云端）之间的空白
```
┌──────────────────────────────────────────┐
│  vLLM/SGLang (云端推理)                   │
│  - K8s + GPU集群                          │
│  - 部署复杂，成本高                       │
└──────────────────────────────────────────┘
                    ↕
         【本文研究填补此空白】
                    ↕
┌──────────────────────────────────────────┐
│  边缘推理共享节点 (本文方案)              │
│  - 单台设备（树莓派/NUC）                 │
│  - HTTP API多用户访问                     │
│  - 跨用户KV-Cache共享                     │
```

## 二、研究意义

### 2.1 理论意义

1. **边缘共享推理架构**：提出面向家庭/小团队场景的轻量级LLM共享推理架构
2. **跨用户缓存复用**：设计跨用户KV-Cache共享机制，提升资源利用率
3. **资源受限下的调度策略**：针对单机多用户场景的动态批处理与优先级调度
4. **隐私-便利平衡**：探索本地化部署与远程访问的最佳实践

### 2.2 实际意义

1. **降低使用门槛**
   - 家庭只需一台设备（如树莓派4B），无需每人购买高端电脑
   - 成本对比：一台共享节点（$50-200）vs 多台GPU工作站（$1000+/台）

2. **保护数据隐私**
   - 代码审查、文档处理等敏感数据不上传云端
   - 满足企业内网、医疗、教育等隐私敏感场景

3. **拓展应用场景**
   - 弱网/离线环境（山区、船舶、野外作业）
   - 移动设备使用（手机/平板通过WiFi调用）
   - IoT设备接入（智能家居、机器人等）

4. **节省长期成本**
   - 避免云端API按token计费
   - 适合重度使用场景（如代码助手、文档生成）

## 三、国内外研究现状与空白

### 3.1 云端LLM推理优化

**代表工作**：
- **vLLM** (UC Berkeley, 2023): PagedAttention，虚拟内存管理KV-Cache
- **Orca** (Microsoft, 2022): 选择性批处理，针对数据中心优化吞吐
- **FlexGen** (Stanford, 2023): 高吞吐offloading策略

**局限性**：
- 目标场景：数据中心GPU集群，优化目标为高吞吐
- 不适用于边缘设备：需要K8s、分布式调度、高速互联
- 未考虑多用户隐私隔离与跨用户缓存共享

### 3.2 边缘设备LLM推理

**代表工作**：
- **Ollama** (2023): 单机LLM部署工具，CLI交互
- **llama.cpp** (2023): 高效C++推理引擎，支持量化
- **MLC-LLM** (CMU, 2023): 移动端部署优化

**局限性**：
- 单用户场景：无多用户管理、无远程访问
- 缓存不共享：每个会话独立计算，无法跨用户复用
- 资源利用率低：串行处理请求，GPU/CPU利用率不足

### 3.3 KV-Cache优化研究

**代表工作**：
- **SGLang** (2024): RadixAttention，基于Trie树的前缀缓存
- **vLLM Prefix Caching** (2024): 自动前缀检测与缓存
- **LMCache** (2024): 企业级KV-Cache分层存储（GPU/CPU/SSD）

**局限性**：
- 单用户视角：未考虑跨用户缓存共享
- 云端场景：假设充足资源，未优化边缘设备内存受限问题

### 3.4 研究空白

本文针对以下空白展开研究：

1. **跨用户KV-Cache共享机制缺失**
   - 现有方案：每用户独立缓存，无法共享
   - 本文方案：全局模板预热 + 跨用户复用

2. **边缘共享节点架构空白**
   - 现有方案：单机本地（Ollama）或云端集群（vLLM）
   - 本文方案：一台设备服务多用户，HTTP API访问

3. **多用户资源隔离与调度**
   - 现有方案：单用户串行处理
   - 本文方案：多用户并发请求的优先级调度与配额管理

4. **统一内存架构利用不充分**
   - 现有方案：主要针对独立GPU优化
   - 本文方案：针对Apple Silicon等统一内存架构优化

## 四、研究内容与关键问题

### 4.1 研究总体目标

**系统目标**：设计并实现面向边缘共享节点的轻量级LLM推理服务系统

**性能目标**：
- 平均响应延迟 < 1秒（vs 基线2-3秒）
- 多用户吞吐提升 2-4倍
- 内存占用 ≤ 8GB（模型+KV+系统）
- KV-Cache命中率 > 40%（跨用户共享场景）

**部署目标**：
- 支持树莓派4B（8GB）/ Intel NUC等低成本设备
- 一键部署脚本，10分钟内完成安装
- 支持3-10个并发用户

### 4.2 关键科学问题

#### **问题1：跨用户KV-Cache复用机制设计**

**挑战**：
- 如何识别不同用户请求中的可复用前缀？
- 如何设计全局缓存结构支持快速匹配？
- 如何在有限内存下平衡缓存容量与命中率？

**难点**：
- 前缀匹配算法的时间复杂度优化
- 缓存淘汰策略（LRU vs 频率 vs 用户公平性）
- 跨用户缓存隔离与共享的权衡

#### **问题2：多用户并发请求的动态批处理调度**

**挑战**：
- 如何在资源受限下提升多用户并发吞吐？
- 如何权衡批处理等待时间与响应延迟？
- 如何根据KV命中率调整调度策略？

**难点**：
- 请求到达时间不均匀，批大小动态调整
- 长短请求混合，避免长请求饿死短请求
- 缓存命中的请求计算量更小，需重新估计优先级

#### **问题3：多租户资源隔离与公平性保障**

**挑战**：
- 如何防止单用户占满计算资源？
- 如何保证用户间的公平性与隐私隔离？
- 如何设计用户配额与流控机制？

**难点**：
- 实时监控每用户资源占用
- 动态调整用户权重与优先级
- 恶意请求检测与限流

## 五、研究方案

### 5.1 方案一：跨用户KV-Cache复用机制

#### 5.1.1 核心思想

不同用户/会话中相同或相似的前缀（如system prompt、代码模板），共享已计算的KV-Cache，避免重复prefill计算。

#### 5.1.2 技术方案

**（1）前缀自动识别**
```
用户A请求：<|system|>你是代码专家<|user|>修复bug...
用户B请求：<|system|>你是代码专家<|user|>重构函数...
                   ↓
        可复用前缀：<|system|>你是代码专家
```

- Token级精确匹配
- 最长公共前缀（LCP）算法
- 预定义模板预热（启动时加载常用模板）

**（2）全局缓存管理**

数据结构：Prefix Tree（前缀树）
```cpp
struct PrefixTreeNode {
    int token;                           // 当前token
    int seq_id;                          // 对应的llama.cpp序列ID
    std::unordered_map<int, Node*> children;  // 子节点
    int hit_count;                       // 命中次数
    time_t last_used;                    // 最后使用时间
};
```

缓存策略：
- **容量管理**：动态调整（根据可用内存）
- **淘汰策略**：LRU + 频率混合
  - 优先淘汰：低频 + 长时间未用
  - 保护高频模板（如预热的代码模板）

**（3）底层集成（基于llama.cpp）**

- 使用 `llama_kv_cache_seq_cp()` 复制KV序列
- 每个缓存条目对应一个 `seq_id`
- 命中时：复制已有序列，跳过prefill
- 未命中：正常计算，并保存到缓存

**（4）Apple Silicon统一内存优化**

- CPU/GPU共享内存，减少拷贝开销
- Metal后端优化，充分利用GPU算力
- 内存池管理，避免频繁分配/释放

#### 5.1.3 预期效果

- **缓存命中率**：40-60%（跨用户共享场景）
- **延迟降低**：命中时延迟降低 60-80%
- **吞吐提升**：减少prefill计算，吞吐提升 2-3倍

---

### 5.2 方案二：多用户动态批处理调度

#### 5.2.1 核心思想

根据请求到达时间、预估计算量、KV命中率等，动态组batch并行处理，提升GPU/CPU利用率。

#### 5.2.2 技术方案

**（1）请求分桶策略**

根据预估计算量分类：
```
┌─────────────────────────────────────┐
│  短请求桶 (< 50 tokens)             │
│  - 快速响应，优先处理                │
│  - 命中KV-Cache的请求                │
└─────────────────────────────────────┘
┌─────────────────────────────────────┐
│  中请求桶 (50-200 tokens)           │
│  - 平衡批大小与延迟                  │
└─────────────────────────────────────┘
┌─────────────────────────────────────┐
│  长请求桶 (> 200 tokens)            │
│  - 允许更长等待，提升吞吐            │
└─────────────────────────────────────┘
```

**（2）批成形策略（Batch Formation）**

触发条件（满足任一即触发）：
- 同桶请求数达到阈值（如8个）
- 最早请求等待时间超过上限（如50ms）
- 预估总计算量达到最优值

批大小动态调整：
```python
max_batch_size = min(
    可用内存 / 单请求KV大小,
    GPU并行度 * 2,
    16  # 上限
)
```

**（3）优先级调度**

优先级计算公式：
```
Priority = α * (1/est_latency) + β * wait_time + γ * cache_hit_boost

其中：
- est_latency: 预估延迟（tokens × 推理速度）
- wait_time: 已等待时间（防饿死）
- cache_hit_boost: 命中KV-Cache时加权
- α, β, γ: 权重系数（可配置）
```

调度策略：
- 短请求优先（提升用户体验）
- 长期等待提权（防止饿死）
- KV命中请求优先（计算量小）

**（4）用户配额与流控**

每用户限制：
- 最大并发请求数（如3个）
- 每分钟请求数上限（如60个）
- 总token配额（如10000 tokens/天）

流控策略：
- 超额请求进入队列或返回429
- 实时监控每用户资源占用
- 动态调整用户权重

#### 5.2.3 预期效果

- **吞吐提升**：2-4倍（vs 串行处理）
- **延迟控制**：P99延迟 < 2秒
- **资源利用率**：GPU利用率从30% → 70%+

- ✅ **Prefix Tree经典**：数据结构成熟，实现难度低
