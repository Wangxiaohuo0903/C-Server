## 深度分析

### 1. K值对延迟的影响

```
K=3 → K=5: 延迟降低40.6% (-3270ms)
K=5 → K=7: 延迟降低1.4% (-69ms)
K=3 → K=7: 延迟降低41.5% (-3339ms)
```

**洞察**: K从3到5收益巨大，从5到7收益递减但仍为正

### 2. K值对接受率的影响

```
K=3: 59.06%
K=5: 72.14% (+22.2%) 🌟 峰值
K=7: 64.94% (-10.0%)
```

**曲线特征**: 先升后降
- K太小(3): 接受率低，因为Draft的token太少，容易被reject
- K适中(5): 接受率最高，平衡了质量和数量
- K较大(7): 接受率略降，因为Draft的token越多越难全部被接受

**但是！**: 虽然K=7接受率比K=5低，但延迟反而更短，为什么？

### 3. 步数分析 (关键！)

```
完成100 tokens所需步数:

K=3: 100 / (3 * 0.5906) ≈ 56步
     总时间 ≈ 56 * (223 + 104) = 18,312ms (理论)
     实际: 8054ms

K=5: 100 / (5 * 0.7214) ≈ 28步
     总时间 ≈ 28 * (266 + 131) = 11,116ms (理论)
     实际: 4784ms

K=7: 100 / (7 * 0.6494) ≈ 22步
     总时间 ≈ 22 * (326 + 180) = 11,132ms (理论)
     实际: 4715ms ✅
```

**关键洞察**:
```
步数减少 > Draft时间增加 > 接受率下降

K=7虽然:
- Draft慢60ms (vs K=5)
- 接受率低7%
但:
- 步数少21% (22步 vs 28步)
→ 总延迟更短
```

### 4. Draft时间分析

```
K=3: 223ms (baseline)
K=5: 266ms (+19.3%, +43ms)
K=7: 326ms (+46.2%, +103ms vs K=3; +22.6%, +60ms vs K=5)
```

**线性增长**: 每增加2个K，Draft时间增加~50ms
- 原因: Drafter生成更多token需要更多推理时间
- 增长比例: ~25ms/token

### 5. Verify时间分析

```
K=3: 104ms (baseline)
K=5: 131ms (+26.0%, +27ms)
K=7: 180ms (+73.1%, +76ms vs K=3; +37.4%, +49ms vs K=5)
```

**非线性增长**: K越大，Verify时间增长越快
- 原因: 批量验证K个token，复杂度可能>O(K)
- 增长比例: 不是线性的，可能是O(K log K)或更高

### 6. 为什么K=7最优？

#### 数学推导

设:
- T_draft(K) = Draft时间(K)
- T_verify(K) = Verify时间(K)
- A(K) = 接受率(K)
- N = 100 (目标token数)

总延迟:
```
Latency(K) = Steps(K) * [T_draft(K) + T_verify(K)]

其中:
Steps(K) = N / (K * A(K))

代入实际值:

K=3:
Steps = 100 / (3 * 0.5906) = 56.4步
Latency = 56.4 * (223 + 104) = 18,443ms

K=5:
Steps = 100 / (5 * 0.7214) = 27.7步
Latency = 27.7 * (266 + 131) = 10,997ms

K=7:
Steps = 100 / (7 * 0.6494) = 22.0步
Latency = 22.0 * (326 + 180) = 11,132ms
```

**理论上K=5应该更快！**

但实际:
- K=5: 4784ms
- K=7: 4715ms

**差异原因** (推测):
1. **缓存效应**: K=7每步Draft 7个token，KV-Cache复用更高效
2. **批处理优势**: 验证7个token的batch效率可能比验证5个token高
3. **GPU并行**: K=7的batch验证可能更好地利用GPU并行

## 最优配置推荐

### 🏆 推荐: K=7

**理由**:
1. ✅ 延迟最低: 4715ms (比K=5快1%, 比K=3快42%)
2. ✅ 吞吐最高: 0.021 tokens/ms
3. ✅ 理论加速最高: 4.55x
4. ✅ 接受率足够: 64.94% (虽不如K=5的72%，但足够高)
5. ✅ 步数最少: 22步 (K=5需要28步，K=3需要56步)

**适用场景**:
- 代码生成任务 (高接受率保证)
- 追求最低延迟
- GPU性能充足 (能承受326ms Draft时间)

### 备选: K=5

**理由**:
- 接受率最高: 72.14%
- 延迟仅慢1%: 4784ms vs 4715ms
- Draft时间更短: 266ms vs 326ms

**适用场景**:
- 追求接受率最大化
- 对话/问答任务 (接受率可能波动更大)
- GPU性能一般 (Draft时间敏感)

### ❌ 不推荐: K=3

**原因**:
- 延迟慢71%
- 接受率低18%
- 吞吐低75%
- 无任何优势

## 结论

### 关键发现

1. **K=7是当前最优配置**
   - 延迟最低: 4715ms
   - 吞吐最高: 0.021 tokens/ms
   - 比K=5快1%, 比K=3快42%

2. **接受率不是唯一指标**
   - K=5接受率72% > K=7的65%
   - 但K=7延迟更短
   - 原因: 步数减少 > 接受率下降

3. **步数是关键**
   - 减少步数带来的收益 > Draft/Verify时间增加的损失
   - K=7 (22步) vs K=5 (28步): 少21%步数

4. **Draft时间是瓶颈**
   - K=7: Draft 326ms, Verify 180ms
   - Draft占64%总时间
   - 优化方向: 更小/更快的Drafter

### 公式总结

```
最优K值满足:

minimize: N / (K * A(K)) * [T_draft(K) + T_verify(K)]

其中:
- N: 目标token数
- K: draft token数
- A(K): 接受率函数
- T_draft(K): Draft时间函数
- T_verify(K): Verify时间函数

DeepSeek-Coder-6.7B + 1.3B组合:
最优K = 7

通用规律 (推测):
- 高接受率(>65%): 增大K直到Draft时间过长
- 中接受率(45-65%): K=5-7
- 低接受率(<45%): K=3-5
```
