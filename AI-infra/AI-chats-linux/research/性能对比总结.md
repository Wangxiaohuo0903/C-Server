## 一、研究背景与目标

### 1.1 研究问题

大语言模型（LLM）推理服务中，**prompt处理阶段（prefill）**消耗大量计算资源，尤其是在：
- 多轮对话场景：每轮都包含完整历史+system prompt
- 相似请求场景：大量用户使用相同的对话模板

**核心挑战**：如何避免重复计算相同的prompt前缀？

### 1.2 优化目标

实现跨请求的KV-Cache复用机制，显著降低推理延迟，提升吞吐量。

**预期指标**：
- 延迟降低：50%+
- 吞吐量提升：2x+
- 缓存命中率：60%+

## 二、技术方案演进

### 2.1 v1策略 (baseline)

**前缀提取规则**：
```
提取最后一个 <|user|> 之前的所有内容作为前缀
```

**示例**：
```
第1轮：<|system|>You are helpful<|assistant|>Hi!<|user|>Q1
        前缀：<|system|>You are helpful<|assistant|>Hi!

第2轮：<|system|>You are helpful<|assistant|>Hi!<|user|>Q1<|assistant|>A1<|user|>Q2
        前缀：<|system|>You are helpful<|assistant|>Hi!<|user|>Q1<|assistant|>A1
```

**问题**：
- 每轮对话的前缀都不同（包含完整历史）
- 导致缓存条目快速增长，命中率低
- 对话越长，前缀越长，越难复用

### 2.2 v2策略 (optimized)

**前缀提取规则**：
```
只缓存第一轮完整对话（到第二个<|user|>之前）
```

**示例**：
```
第1轮：<|system|>You are helpful<|assistant|>Hi!<|user|>Q1
        前缀：（不提取，需要≥2轮）

第2轮：<|system|>You are helpful<|assistant|>Hi!<|user|>Q1<|assistant|>A1<|user|>Q2
        前缀：<|system|>You are helpful<|assistant|>Hi!<|user|>Q1<|assistant|>A1<|user|>
        （第一轮完整对话+第二个<|user|>标记）

第3轮及以后：前缀保持不变！
```

**优势**：
- 相同chat_id的所有后续请求都复用相同的固定前缀
- 缓存条目数量稳定，不随对话轮次增长
- 大幅提升命中率

## 五、核心技术实现

### 5.1 数据结构设计

```cpp
struct PrefixCacheEntry {
    std::string prefix_text;      // 前缀文本（匹配key）
    int seq_id;                   // llama.cpp序列ID
    int kv_length;                // 前缀token数量
    uint64_t last_used_ns;        // 最后使用时间（纳秒）
    uint32_t hit_count;           // 命中次数
};

// 缓存池（哈希表，O(1)查找）
std::unordered_map<std::string, PrefixCacheEntry> prefix_cache_;
static constexpr size_t MAX_PREFIX_CACHE = 32;
```

### 5.2 llama.cpp零拷贝集成

```cpp
// 缓存命中时：复制KV cache到当前推理序列
llama_kv_cache_seq_rm(ctx_, 0, 0, -1);  // 清空seq_id=0
llama_kv_cache_seq_cp(ctx_, cached_seq_id, 0, 0, kv_length);

// 保存时：将当前KV复制到新序列永久保存
int new_seq_id = next_seq_id_++;
llama_kv_cache_seq_cp(ctx_, 0, new_seq_id, 0, kv_length);
```

**关键技术点**：
- 使用llama.cpp的`seq_id`机制隔离不同序列的KV cache
- `seq_cp`是零拷贝操作，只复制指针，不复制数据
- 每个缓存前缀占用独立的seq_id，互不干扰

### 5.3 LRU淘汰策略

```cpp
void ModelManager::evictLRU() {
    if (prefix_cache_.empty()) return;

    // 找到最久未使用的条目（最小last_used_ns）
    auto oldest = prefix_cache_.begin();
    for (auto it = prefix_cache_.begin(); it != prefix_cache_.end(); ++it) {
        if (it->second.last_used_ns < oldest->second.last_used_ns) {
            oldest = it;
        }
    }

    // 删除该序列的KV cache
    llama_kv_cache_seq_rm(ctx_, oldest->second.seq_id, 0, -1);

    // 从缓存池移除
    prefix_cache_.erase(oldest);
}
```

**优化方向**：
- 当前：纯LRU（只看last_used_ns）
- 未来：LRU + hit_count加权（高频缓存优先保留）

## 六、性能瓶颈分析

### 6.1 当前命中率仍然偏低（26.3%）

**原因分析**：
1. **测试数据特点**：
   - 共享前缀场景中，只有第2+轮请求能命中缓存
   - 第1轮请求总是miss（需要≥2轮才提取前缀）
   - 20个请求中，实际只有~19个有机会命中

2. **前缀提取时机**：
   - 当前：第2轮对话开始时才提取并缓存
   - 改进：第1轮对话结束后立即缓存system prompt部分

**改进方案**：
```cpp
// 优化：在第1轮对话结束后就缓存固定的system prompt
if (chat_sessions_[chat_id].messageCount() == 2) {  // 1轮完整对话
    // 提取system prompt + 第一个user/assistant交互
    std::string fixed_prefix = extractFirstRoundPrefix(prompt);
    savePrefixCache(fixed_prefix, computeTokenLength(fixed_prefix));
}
```

**预期提升**：
- 命中率从26.3%提升至**60-80%**
- 第1轮之后的所有请求都能命中

### 6.2 P95延迟未改善

**现象**：
- 平均延迟显著降低（-69.8%）
- P95延迟反而略有上升（1472ms → 1596ms）

**原因分析**：
- **长尾效应**：少数请求遇到缓存未命中+生成超长回复
- **LRU淘汰**：在缓存池满时，淘汰操作引入额外延迟
- **内存碎片**：频繁的seq_cp/seq_rm可能导致Metal内存碎片

**改进方案**：
1. 增加缓存容量（32 → 64），减少淘汰频率
2. 异步淘汰：在后台线程执行evictLRU()
3. 预分配KV cache空间，减少动态分配overhead

## 七、未来优化方向

### 7.1 短期优化（1-2周）

**目标**：命中率提升至50%+

1. **支持用户自定义system prompt**
   ```cpp
   // API扩展
   POST /chat
   {
       "user": "xiaohuo",
       "system_prompt": "You are a helpful coding assistant..."
   }
   ```
   - 允许用户指定固定的system prompt
   - 自动识别并缓存这部分
   - 不同用户共享相同的system prompt缓存

2. **缓存预热机制**
   ```cpp
   // 服务启动时预加载常用模板
   const std::vector<std::string> COMMON_PROMPTS = {
       "You are a helpful assistant.",
       "You are a coding expert.",
       "You are a teacher..."
   };

   void ModelManager::warmupCache() {
       for (const auto& prompt : COMMON_PROMPTS) {
           // 预计算KV cache并存储
           precomputeAndCache(prompt);
       }
   }
   ```

3. **基于token边界的前缀截断**
   - 当前：按字符串查找`<|user|>`截断
   - 优化：tokenize后按token数量截断，更精确

### 7.2 中期优化（3-4周）

**目标**：实现GPU/CPU冷热分层

```
高频cache (hit_count > 10) → Pin在GPU显存
低频cache (hit_count < 5)  → 迁移到CPU主存

访问时：
- GPU cache → 直接使用（零拷贝）
- CPU cache → 传输到GPU（~1-2ms overhead）
```

**技术方案**：
- 使用Metal Unified Memory（macOS）
- CUDA Managed Memory（NVIDIA GPU）
- 监控hit_count，动态调整分层阈值

### 7.3 长期优化（2-3个月）

**目标**：Prefix Tree（Trie）结构

```
当前：HashMap查找，只支持完全匹配
未来：Trie树，支持最长公共前缀匹配

示例：
prefix1 = "You are a helpful coding"
prefix2 = "You are a helpful math"

共享前缀 = "You are a helpful"  ← 可以复用这部分KV cache
```

**优势**：
- 节省存储空间（公共前缀只存一份）
- 支持部分前缀复用
- 提升命中率（语义相似的prompt也能部分复用）

## 八、学术价值与贡献

### 8.1 技术创新点

1. **跨请求KV cache全局共享**
   - 现有系统（vLLM、FlexGen）：单会话内缓存
   - 本工作：跨用户/跨会话的全局缓存池
   - 适用于multi-tenant SaaS场景

2. **固定前缀提取策略**
   - v1问题：随对话增长，前缀不断变化
   - v2创新：只缓存第一轮固定前缀
   - 效果：命中率提升5倍（5.3% → 26.3%）

3. **零拷贝llama.cpp集成**
   - 直接利用llama.cpp原生seq_cp API
   - 避免KV cache数据复制overhead
   - 可移植到其他llama.cpp项目
